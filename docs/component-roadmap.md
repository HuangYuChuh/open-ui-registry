# 首批组件路线图

## 目标

在现有航班状态卡片的完整流程基础上，再完成 9 个已验证组件，使第一版达到 10 个组件。首批组件应覆盖常见产品工作流，而不是堆叠外观相似的展示组件。

本路线图只定义产品槽位，不代表任何第三方实现已经通过许可证审查。确定上游来源前不得复制、适配或发布源码。

## 选型优先级

候选组件按以下顺序评估：

1. 解决明确且常见的产品问题。
2. 相比基础 shadcn 组件具有明显的组合、交互或视觉价值。
3. 许可证明确允许修改和再分发，并能锁定到具体版本或提交。
4. 能适配 React、TypeScript、Tailwind CSS 和 CSS 变量。
5. 依赖数量与包体成本合理，不要求隐藏的全局 Provider 或样式。
6. 能提供适合中文内容长度、中文输入和中文屏幕阅读器的体验。
7. 在 375px、768px、1024px 和 1440px 下具有可靠布局。

## 推荐实施顺序

先实现文件上传队列、空状态与活动时间线。这三个方向分别覆盖高价值交互、低风险基准组件和结构化数据展示，可以尽早验证 Registry 对复杂度不同组件的适配能力。

AI 提示词输入器应在输入法组合事件测试方案确定后开始。看板和通知中心涉及更复杂的焦点、拖放或弹层交互，安排在基础测试设施完善之后。

## 单个组件进入开发前的证据

每个候选实现必须先建立审查记录，至少包含：

- 原作者或组织；
- 演示 URL、仓库 URL 和确切源文件 URL；
- 上游版本、标签或提交；
- SPDX 许可证标识及许可证文件 URL；
- 许可证适用范围和再分发审查结论；
- 运行时与开发依赖；
- 与现有组件和基础 shadcn 组件相比的新增价值；
- 计划修改内容；
- 中文内容、输入法、响应式和无障碍测试要点。

## 首个候选的通过条件

文件上传队列只有满足以下条件才进入源码适配：

1. 上游许可证明确允许修改和再分发。
2. 拖放不是唯一操作方式，键盘和文件选择器可以完成同一任务。
3. 上传中、成功、失败和取消状态都有可读文本与程序化语义。
4. 中文文件名和较长错误信息不会破坏布局。
5. 网络上传逻辑由使用方注入，Registry 组件不绑定特定存储服务。
6. 依赖在 Registry 元数据中逐项声明。

当前上游候选及许可证与技术初审记录见 [文件上传队列候选审查](candidates/file-upload-queue.md)。该候选尚未获得维护者选型确认，不得描述为已收录或已验证。

## 暂不优先

- 只改变背景或装饰效果、缺少明确产品用途的组件；
- 与现有 shadcn 基础组件几乎等价的简单包装；
- 强依赖特定品牌、字体、图片或图标资产的组件；
- 需要大型运行时、状态管理框架或整站 Provider 的孤立组件；
- 无法提供完整许可证证据的公开视频、帖子或演示代码。
